代码只跑了一小会儿，为什么容器至少按五分钟计？

OpenAI 的代码解释器和托管 Shell 走同一行容器价。价目表按每 20 分钟、每只容器写一档，脚注又写：符合条件的会话按分钟计，一次会话最少 5 分钟。内存分 1、4、16、64 四档，选定之后跟这只容器走完。闲置满 20 分钟，容器过期，里面的文件和 Python 对象一起丢掉。模型自己的 token 仍按所选模型另计。

核验清单

  • ✓先确认这一列是容器会话，商品覆盖代码解释器和托管 Shell。模型 token 仍按所选模型另计。
  • ✓价目行按每 20 分钟一档写。脚注写符合条件的会话按分钟计，并有 5 分钟下限。两句不要加成两笔。
  • ✓内存档在容器存活期间改不了。省略时是 1 GB。更高档按内置工具费率计，单价以价目页为准。
  • ✓闲置 20 分钟过期，过期后不能救活。查询、增删文件会刷新 last_active_at。文件要在过期前下载。
  • ✓自动模式会复用上下文里仍存活的容器。上下文里没有上一次调用时，新会话可以再次碰上 5 分钟下限。

1. 同一页上有两句计费单位

OpenAI 价目页把容器单独列成一行，覆盖范围写的是托管 Shell 和代码解释器。四档内存并排：1 GB、4 GB、16 GB、64 GB，单位是每 20 分钟、每只容器。同一页的说明紧接着写：符合条件的容器会话按分钟计，一次会话最少 5 分钟。页上用的 GB 是二进制，1 GB 等于 2 的 30 次方字节。内置工具用掉的 token，仍按所选模型的 token 单价计。Responses、Chat Completions、Realtime、Batch、Assistants 这几套接口本身不再另收一层接口费，token 按模型的输入和输出价计。容器是加在 token 旁边的那一列。

对账时最容易把这两句加成两笔。一行说「每 20 分钟一档」，脚注说「按分钟，最少 5 分钟」。脚本只跑了几十秒，按脚注已经落到 5 分钟这档下限。把 20 分钟再加一次，等于把价目行和脚注当成两次收费。反过来，把几十秒记成零，又把下限漏掉。页上的「符合条件」没有在同一段里展开成清单。账单上的会话时长，才是判断这一只容器落在哪一句上的依据。单价留在价目页，这里只记单位：档、分钟、下限。

这列和另外两本海外账分开。向量库按天计存储，免费额度按全部库合计，调用费另计。函数定义按输入计，函数没被点到，定义文本仍在输入里。容器计的是这只沙箱活了多久、内存开在哪一档。三列可以出现在同一次请求里：定义占输入，检索结果再占输入，容器按会话走。只拿输出字数去除以单价，三列都会对不上。

2. 内存档跟容器走完，自动模式也会复用

代码解释器说明把容器写成一只完全隔离的虚拟机，模型在里面跑 Python。可选 1g、4g、16g、64g。不写 memory_limit 时保持默认的 1 GB。选定的档位覆盖这只容器的整个存活期，自动创建和通过容器接口显式创建都一样。更高档按代码解释器的内置工具费率计。想换档，就要新开一只容器，旧的那只仍按它出生时的档走完。

自动模式在创建 Response 时传入 container.type = auto。它会新建一只容器，或者复用模型上下文里上一次 code_interpreter_call 用过、并且仍处于活动状态的那只。输出里的 code_interpreter_call 带有这次生成或复用的 container_id。显式模式先打 v1/containers，把返回的 id 填进工具配置。自动创建的容器同样能在 /v1/containers 上查到。模型把这个工具认成 python tool。提示里直接写 python tool，比只写代码解释器更明确。

所以「又发了一次 HTTP」推不出「又开了一只容器」。上下文里还留着上一次的调用，容器也没过期，自动模式续的是同一只。续上的会话继续走原来的内存档，也继续走原来那只钟。上下文被截掉、上一次调用不在里面，自动模式就会再开一只。新的一只可以再次碰上 5 分钟下限。把每一轮对话都当成新会话去估，短任务会被估高。把一整天都当成一只容器去估，截断上下文之后的新下限又会被估漏。

3. 过期是 20 分钟，查询会把这只钟拨回去

容器闲置满 20 分钟就过期。过期之后，再把它放进 v1/responses 会失败。元数据快照还在，容器里的数据从系统里清掉，找不回来。过期状态不能拨回活动。做法是新建一只，把文件重新传上去。旧容器内存里的 Python 对象一并丢失。说明建议把容器当成临时的，相关数据放在自己的系统里，需要的文件要在它还活动时下载。

任何容器操作都会刷新 last_active_at。文档点名的操作包括：查询这只容器，往里面加文件，从里面删文件。这只钟管的是「再闲 20 分钟就过期」，它和价目页上的会话计费写在两处。一次查询可以让容器躲过过期，账单上是否把两次查询之间的空档按分钟计，页上没有另写一条。健康检查如果只是为了让容器别死，它同时把过期推迟了。把每一次 GET 都记成一笔新的 5 分钟下限，页上没有这句话。把轮询期间整段都当成免费，页上也没有这句话。对账看这只容器的会话时长，再对照 5 分钟下限，而不是用请求次数乘下限。

模型生成的文件出现在下一条消息的 annotations 里，类型是 container_file_citation，带 container_id、file_id 和文件名。下载走容器文件内容接口。放进模型输入的文件会自动上传到容器，不必为了同一只容器再传一次。容器过期之后，引用还在消息里，字节已经不在。先下载，再让它闲置，这两步的顺序写在过期规则里。

4. 重试加的是 token，新下限看是不是新容器

说明里的用法包括：模型写出跑失败的代码，可以继续改、继续跑，直到成功。这些重试如果还在同一只活动容器里，内存档不变，Python 里已经建好的对象还在。多出来的是模型来回改写的 token，内置工具的 token 按所选模型计。容器费跟着这只会话走。语法错误的次数，本身不是容器的计费单位。

一旦这只容器过期，或者新的请求上下文里没有上一次的 code_interpreter_call，自动模式会再开一只。新的一只重新适用内存档，也重新面对会话下限。显式传入旧 id 时，过期的那只直接失败，救不活，只能新建并重新上传。tool_choice 设成 required，是要求这次调用必须用到该工具。它改变的是工具会不会被点到，不改变会话按分钟计、最少 5 分钟这一句。

文件体积和内存档也不是同一把尺。档位名字里的 GB 是内存，并且是 2^30 字节。一份按十进制算出来的上传大小，对不上档位名字，是预期。向量库那一列按解析后的分块和嵌入体积按天计，和这只沙箱的内存档无关。把上传前的文件兆字节，当成容器该开 4 GB 还是 16 GB 的理由，两套单位都用错了。

5. 充值缩不掉这 5 分钟

对账按五列走。第一列是商品：容器会话、模型 token、向量库存储，各自保留。第二列是这只容器的标识，看这次是复用还是新建。第三列是会话时长和 5 分钟下限，价目行的 20 分钟一档与脚注放在一起读，不加成两笔。第四列是内存档，出生时定下，活着的时候不改。第五列是过期钟：last_active_at 是否被查询或增删文件拨过，文件是否在过期前下载。

给账户准备额度，发生在这些列扣款之前。链上把稳定币换成能付进账户的资产，不会把几十秒的脚本收成零，也不会把 4 GB 那只容器改回 1 GB。需要这一步时，可以用无需注册、非托管的 AllSwap 完成链上兑换。兑换成功只说明资产换了手。容器的下限、内存档和模型 token 仍按这次实际开着的那只容器计。
