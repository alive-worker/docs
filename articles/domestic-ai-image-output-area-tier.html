参考图很小，为什么输入档却跟着输出的像素面积走？

阿里云百炼的千问图像不按提示词的 token 计。价格页的公式是输入图像张数乘输入单价，加上成功生成的输出张数乘输出单价。没写输入单价的模型，输入不计。qwen-image-3.0 的用量把输入档和输出档都按输出图像的像素面积划分：不超过 2,250,000 像素记 1K，超过记 2K。参考图自己是一张小图，也不改这个分界。请求 4 张、只返回 3 个地址，计的是 3 张。单价、地域和活动留在价格页和控制台。

核验清单

  • ✓先看用量是不是图片计量。3.0 返回 input_image_count 和 output_image_count，接口写明这不是 token。
  • ✓输入档和输出档都按输出像素面积分。面积不超过 2,250,000 是 1K，超过是 2K。参考图自己的宽高不决定这一档。
  • ✓价格页没写输入单价的模型，输入不计。3.0 有输入行。2.0 系列的表只写输出单价。
  • ✓计成功返回的张数，不计请求的 n。示例是要 4 张、成功 3 张，计 3 张。组图模式下省略 n，上限默认 12，实际张数不超过这个上限。
  • ✓请求失败不产生费用，也不消耗免费额度。北京地域 3.0 的免费额度是输入和输出共用，其他地域没有。单价以价格页为准。

1. 计的是张数，用量对象不是 token

模型价格页把图像生成写成：按输入图像和成功生成的图像张数计费。没有写明输入图像价格的模型，输入不计费，只计输出。公式在同一处：费用等于输入图像单价乘输入张数，加上输出图像单价乘输出张数。请求失败不产生任何费用，也不消耗免费额度。价格页写明展示的是调用原价，活动在控制台。本文不把某一天的元价写成长期牌价。

图像生成与编辑的接口说明把 3.0 的 usage 定义成图片输入和输出的计量，并直接写明：这里不是 token 用量。文生图时 input_image_count 为 0。图生图按实际传入的图片数返回。理解一张图要折成多少 token，见调用DeepSeek、通义千问图片理解API，一张图到底折算成多少token，不能拿来估这一次出图。提示词再长，截断改变的是送进去的字，不把这次调用改成按 token 计费。

所以「加一张参考图」在不同系列上不是同一句话。3.0 的价格表有输入行，接口也返回输入张数。2.0 系列的价格表标题写的是按张计费，表里列出的是输出单价，没有输入单价。按价格页那句规则，没写输入价格的模型，输入不计。2.1 可以传 1 到 10 张参考图，3.0 是 1 到 3 张。张数上限是接口限制。计不计输入，先看价格表有没有那一行，再看 input_image_count 是不是 0。

2. 225 万像素量的是输出，不是那张小参考图

3.0 的 input_image_type 和 output_image_type 用的是同一把尺子，尺子量的是输出分辨率的像素面积。面积小于或等于 2,250,000，输入记 qima_input_1k，输出记 qima_output_1k。面积大于 2,250,000，两边都记 2K。参考图自己是 512 像素宽，只要输出跨过这条线，输入档的名字也是 2K。它不按你上传的那张文件有多小来分。

这条线很好对照。1024×1024 是 1,048,576，停在 1K 这边。1500×1500 正好 2,250,000，仍是小于或等于，还在 1K。2048×2048 是 4,194,304，已经在 2K。接口推荐的 2K 方图就是 2048×2048。不传 size 时，3.0 和 2.1 由模型按提示词推荐分辨率。2.0 系列的默认值直接是 2048×2048。万相图像 wan2.7-image 和 wan2.7-image-pro 的默认是 2K。省略分辨率，不是一次停在小图上的试看。

档位名字和单价行不是同一件事。3.0-pro 的价格表把输出分成 1K 和 2K 两档，两档单价不同。3.0 的表也写出 1K 和 2K，但两档输出单价相同，输入也没有因为 2K 再开一个不同的单价。看到 qima_output_2k，先看模型是 3.0 还是 3.0-pro，再决定这是不是换了一档钱。单价以价格页当时的数字为准。wan2.7-image-pro 的 4K 只在没有图片输入、又不是组图的文生图里可用，其余场景文档写的是只支持 2K。把编辑或组图请求写成 4K，对不上这个支持范围，不要按一次成功的 4K 去估。

3. 要了 4 张，只成功 3 张，就计 3 张

价格页的示例是：请求生成 4 张，实际只成功返回 3 个图像地址，另 1 张失败，系统只对成功生成的图像计费，计费数量是 3 张。示例里的单价是用来演示乘法的假设，不是长期牌价。对账时对的是成功张数，不是参数 n 上写的那个整数。文生图的使用说明把这句话写成：n 直接影响费用，费用等于单价乘成功生成的图片张数。

不传 n，默认是 1，不是 0。千问 3.0 和 2.1 可选 1 到 6 张。万相这两款在关闭组图时是 1 到 4 张。n 必须是整数，写成字符串会返回 400。空的图像数组或 null 也是 400。内容审核拦住的请求同样失败。这些失败落在「请求失败不产生费用」里，不要按 n 的上限去估一张已经生成的图。

组图是另一档默认值。只有 wan2.7-image 和 wan2.7-image-pro 支持 enable_sequential，默认是 false。设成 true 之后，n 表示最多生成多少张，范围 1 到 12，默认 12。实际张数由模型决定，并且不超过 n。费用仍按成功生成的张数乘单价，不是按 12 这个上限先扣满。你没改 n 就打开组图，上限已经是 12。模型若成功交回 8 张，计的是 8，不是 1，也不是先按 12 预扣。思考模式默认开启，文档写的是增加耗时。组图打开时，思考模式和颜色主题不可用。水印默认关闭，打开只是在右下角加上「AI生成」，不另开一张计费表。

4. 失败是零，24 小时是下载钟

整次请求失败，价格页写的是不产生费用，也不消耗免费额度。模型、Endpoint 和 API Key 必须属于同一地域，跨地域调用会失败。异步接口必须带上开启异步的请求头，缺了会报错。任务还在排队或处理中，还没有成功张数。状态变成失败或取消，也不是成功生成。查询任务不会因为你多查一次就再生成一批图。用量出现在调用成功的结果里。

免费额度不要抄成所有模型同一句。价格页写明，千问图像 3.0 这一组只在华北 2（北京）有免费额度，其他地域没有。北京表上 3.0 和 3.0-pro 写的是输入和输出共 10 张，有效期是开通百炼、模型发布、申请通过三者里较晚的那天起 90 天。这是一口共用的额度，不是输入 10 张再加输出 10 张。2.1-pro 和 2.1-turbo 的表写 10 张，没有写成输入输出共用。2.0 那几行写的是无。把 3.0 的共用 10 张套到 2.0 上，会对出一张价格页没有的额度。

图像 URL 的有效期是 24 小时，异步 task_id 的查询有效期也是 24 小时。这是下载和查询的钟。张数在生成成功时已经按用量计过。过了 24 小时再下载失败，不是把那几张退回，也不是按下载次数再计一次。提示词智能改写默认开启，改的是正向提示词的措辞。反向提示词超长会被截断。两处改变的都是字，不是成功张数，也不是那条 225 万像素的分界。视频按秒计，见参考视频有三十秒，为什么输入侧只按五秒这口池计？。这里的输出是张，不是秒。

5. 充值改不了这条像素分界

对账按六列走。第一列是模型：3.0 有输入行和像素分档，2.0 系列的表只写输出单价。第二列是输入张数：文生图是 0，图生图按实际传入的张数，空数组会直接失败。第三列是输出像素面积：不超过 2,250,000 记 1K，超过记 2K，输入档跟着这一刀走。第四列是成功张数，看返回了几个地址，不看 n 的请求值；组图还要看上限是不是默认的 12。第五列是失败和额度：整次失败按零，北京 3.0 的免费额度是输入输出共用。第六列是地域，其他地域没有这一口免费额度。

给账户准备额度，发生在这些列扣款之前。链上把稳定币换成能付进账户的资产，不会把一张小参考图的尺寸写成输入档，也不会把只成功的 3 张改回请求的 4 张。需要这一步时，可以用无需注册、非托管的 AllSwap 完成链上兑换。兑换成功只说明资产换了手。输入张数、输出像素面积和成功张数，仍按这次实际成功的调用计。
